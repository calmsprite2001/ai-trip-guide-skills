# 攻略来源 · 数据从哪来，可信度怎么标

> 这份文件解决本 skill 最容易被质疑的一件事：**攻略里的内容，是查到的，还是编的？**
>
> 结论先行：**本 skill 没有内置任何"景点资料库"**。它不存景点、不存店铺、不存票价。
> 每一份攻略的每一个地址、电话、票价、预约规则，都是**跑这一遍时现查的**。
> 所以「来源」必须成为流程的一部分，而不是可选项。

---

## 一、目的地范围

**目的地 = 用户指定的任何地点，不预设。**

| 范围 | 支持度 |
|---|---|
| **中国内地全部省市区** | ✅ 全流程（12306 + 身份证实名 + 高德导航 + 国内景区预约体系） |
| 中国香港 / 中国澳门 | ⚠️ 主流程可用，需补出入境证件与当地交通模块 |
| 中国台湾 | ⚠️ 主流程可用，需补通行证与当地交通 |
| 出境 | ❌ 不在范围 |

**不含预设线路。** 不存"川西经典 7 日"这类现成模板 —— 用户给什么行程就做什么行程，用户没给城市就先问出来（见 `interview.md`）。

地域差异（配色 / 主力交通 / 证件 / 季节）→ `regions.md`

## 二、来源分层（按可信度，从高到低）

页面上**每一条可核验的数据都必须能落到下面某一层**，并在「核验说明」里写明。

### S1 · 用户提供 ★★★★★

用户自己给的硬事实，**优先级最高**，直接用。

| 内容 | 说明 |
|---|---|
| 已出票的航班 / 车次 / 门票 | 用户给了就是事实，标「已出票」 |
| 已知的开售时间 | 标「用户提供」（区别于推算值） |
| 人数结构、中途变化 | 费用与住宿的唯一依据 |
| 必须赶上的时刻（接人 / 送人） | 作为行程骨架的硬约束 |
| 忌口、预算、节奏偏好 | 直接决定内容密度 |

⚠️ **用户给的也要留个心眼**：涉及记忆型信息（"我记得是 9 点放票"）**关键项必须复核**，页面标「用户提供 · 未复核」。
⚠️ **用户给的信息会中途变**（人数是最典型的），变了一次就要全篇重算。

### S2 · 官方一手源 ★★★★★

**能查到就一定要查到这里。** 这一层的价值是"可以直接引用"。

| 数据 | 官方入口 |
|---|---|
| 火车票 / 起售时间 / 候补规则 | **12306 官网与 App**（App → 我的 → 出行向导 → 起售时间）；国铁集团公告 |
| 机票 | 航司官网 / App（OTA 价格仅供参考） |
| 景区 & 博物馆预约 | **景区官网 + 官方公众号 + 官方小程序**（三者取其一为准，以最新公告为准） |
| 票价 / 开放时间 / 闭馆日 | 同上；政府文旅部门公告 |
| 地址 / 距离 / 导航 | **高德地图 / 百度地图**（导航链接直接生成） |
| 天气 | 中国天气网 / 中央气象台（行程临近时再查，早了不准） |
| 边防证 / 特殊准入 | 当地公安或文旅部门公告 |

**页面上标**：`已核验 · 2026-09-13`

### S3 · 联网搜索 ★★★☆☆

用于**找入口**和**确认变动**，不作为最终依据。

- 手法：先搜「XX景区 预约 官方公告」，**再点进官方页面确认**，别停在搜索结果摘要。
- 搜到二手转载（自媒体、咨询网站）→ 只能当线索，**回头去官方源核实**。
- 搜不到的，**标「未核验，以官方当日公告为准」**，不要编一个看起来合理的答案。
- 时效性内容必须查最新：票价、闭馆日、班次、限流政策**逐季都可能变**。

**页面上标**：`已核验`（若追到了官方源）/ `据公开信息`（二手源）

### S4 · 平台增强（WorkBuddy 环境）

| 能力 | 用途 | 缺失时怎么办 |
|---|---|---|
| `ImageGen` | 生成系列封面图 | **降级**：用纯 CSS 几何封面 / 用户自备照片 / 只保留配色块 |
| `workbuddy_sites_deploy` | 发布在线链接 | **降级**：只交本地 HTML + 离线单文件版（脱网照样用） |
| `markitdown-skill` / `pdfkit-py` | 解析用户给的旧行程书 | 降级：用 `pymupdf` 直接抽文本 |
| `mobile-html-headless-verify` | 移动端验证 | 降级：用 iframe 预览页人工看 |
| `series-illustration-consistency` | 配图风格统一 | 降级：不配图或用同一套 emoji 图标 |

⚠️ **本 skill 不依赖任何金融 / 行情 connector。** 旅游数据不在那些连接器里，
硬塞进去只会拖慢启动（连接器掉绑会导致整个自动化终止）。这条是刻意设计。

### S5 · 模型先验 ★★☆☆☆

**分界线必须划清楚：**

| 可以用 | **绝对不可以** |
|---|---|
| 通用行程节奏（一天几个点合理） | ❌ 具体电话号码 |
| 城市间大致方位与距离量级 | ❌ 门牌号 / 具体地址 |
| 常见景点的大致看点 | ❌ 票价 / 开放时间 / 闭馆日 |
| 常规提醒（周一博物馆多闭馆） | ❌ 预约规则 / 放票时点 |
| 常识性的行前准备 | ❌ 班次号 / 起售时刻 |

**右列一律必须走 S2 或 S3。** 查不到就留空或标「待补」——
**宁可页面缺一行，也不能出现一个编的电话号码。**
用户照着编的地址跑空一趟，整个攻略的信誉就没了。

## 三、各类数据的来源清单（速查）

| 数据类别 | 首选来源 | 交叉核验 | 备注 |
|---|---|---|---|
| **城际交通班次** | 12306 官网 / App；航司官网 | — | 时刻票价以官方为准 |
| **火车票规则** | 12306 官方公告 | 国铁集团公告 | → `ticketing.md` |
| **机票** | 航司官网 / App | OTA 比价 | 廉航常只在官网 |
| **景点门票 / 预约** | **景区官方公众号 / 小程序 / 官网** | OTA（携程 / 美团） | 官方优先；OTA 可能加价或滞后 |
| **开放时间 / 闭馆日 / 票价** | 官方公众号最新公告 | 联网搜索确认变动 | 逐季会变，必查最新 |
| **景点介绍 / 玩法 / 机位 / 避坑** | **小红书高赞攻略**（指定） | 官方导览、马蜂窝、B站 | 经验类内容，**绝不标「已核验」** |
| **🍜 美食 · 店名与招牌菜** | **大众点评**（指定） | 美团；本地美食公众号 | 按评分 + 评论数筛，避开纯网红店 |
| **🍜 美食 · 地址与电话** | **大众点评** | **高德地图（必交叉）** | 单一来源会错，两源一致才写 |
| **地址 / 导航** | 高德地图 | 百度地图 | 直接生成 `uri.amap.com` 链接 |
| **天气** | 中国天气网 / 中央气象台 | — | 临行前 3 天再查才准 |
| **住宿** | 携程 / 美团比价 → 酒店官方直订 | — | 页面报价非最终价 |
| **特产 / 在哪买** | 大众点评 + 本地市场 | 当地公众号 | 标价位 + 挑选要点 |
| **边防证 / 特殊准入** | 目的地公安或文旅部门公告 | 联网搜索 | 涉及就必须单列说明 |

### 美食来源细则（大众点评）

**这是桦哥指定的美食来源。** 执行要点：

1. **找店**：WebSearch 搜「城市 + 大众点评 + 菜系/店名」，或「城市 + 必吃 + 老字号」。
2. **取信息**：店名 · 招牌菜 · 人均 · 评分 · 地址 · 电话 · 营业时间。
3. **页面常需登录**，抓不到时**降级**：搜索结果摘要 + 美团 / 高德 POI 取信息。
4. 🔴 **地址电话必须和高德交叉核** —— 点评地址常是商户自填的旧址，高德 POI 更准。
5. **评分看「口味分 + 评论数」**，评论数 < 500 的新店慎推（可能是刷的）。
6. **同名老字号有分店** —— 必须写清是哪家店（"德顺源·大盛斋店"而不是"德顺源"）。

产出形态 → `data-schema.md` 的 `CITIES[].eat[]`，每城 3–6 家。

### 景点介绍来源细则（小红书）

**这是桦哥指定的景点「介绍」来源。** 但小红书是 UGC，**适用范围必须卡死**：

| ✅ 可以取（经验类，官方没有） | ❌ 绝不能取（必须走官方源） |
|---|---|
| 玩法路线、游览顺序 | **票价** |
| 拍照机位、最佳光线时段 | **预约规则、放票时间** |
| 排队实况、避坑提醒 | **开放时间、闭馆日** |
| 隐藏看点、冷门入口 | **地址、电话** |
| 穿搭 / 装备建议、体力提示 | 班次时刻 |

执行要点：

1. **搜索**：WebSearch 搜「景点名 + 小红书 + 攻略 / 机位 / 避坑」。
2. **取高赞**：优先**收藏数**高的（收藏比点赞更能说明实用）；看发布时间，**超过 1 年的打折**。
3. **去软广**：出现明显商家名、价格引导、联系方式 → 当广告剔除。
4. **交叉**：同一说法有 **3 条以上不同作者**提到，才当共识写进页面。
5. **落到数据**：写进 `CITIES[].shots[]`（拍照点）和 `days[].items[].x` 的提示语里。
6. 🔴 **标注**：页面写「据小红书高赞攻略整理」，**绝不标「已核验」**。
   UGC 经验和个人感受不能冒充官方事实 —— 这是本 skill 的信誉底线。

**降级**：小红书抓不到（需登录 / 反爬）→ 退到马蜂窝 / 知乎 / B站同类内容，同样标注来源。

## 四、"简单信息"能做出什么（预期管理）

开工前先把这张表跟用户对一遍，**避免交付时预期错位**：

| 用户给的信息 | 能产出的攻略 | 明确不做的 |
|---|---|---|
| 只说「想去成都玩 5 天」 | 城市分册骨架 + 通用玩法编排 + 行前提醒 + 配色配图 | **不给具体店铺电话地址**（标"通用推荐，未核具体店铺"） |
| + 航班 / 车次 | 以上 + 逐日行程卡 + 「距出发 N 天」倒计时 | 票务规则仍按推算 |
| + 票务细节（哪些已出、几号开售） | 以上 + 票夹 Tab + 抢票倒计时页 | — |
| + 吃买偏好 | 以上 + 店铺清单（**逐条核实地址电话**） | — |
| + 人数 / 预算 / 节奏 | 完整 8 Tab（总览 + N 城 + 票夹 + 应急） | — |

**核心原则：信息越少，产出越偏"框架"；核不到的数据一律留白标注，绝不用编造内容填充。**
这是本 skill 的底线 —— **框架完整 + 数据诚实** 好过 **内容丰满 + 数据可疑**。

## 五、执行顺序（写进 ③ 核实阶段）

```
1. 列清单   → 这份攻略要写哪些"可核验数据"？（票价/预约/地址/电话/时刻）
2. 分来源   → 每条数据归到 S1~S5 哪一层，标出必须去 S2 核的
3. 查证     → S2 优先；S2 不通走 S3；都不到 → 标「以官方当日公告为准」
4. 记日期   → 每条核验数据记下核验日期（内容会变，日期是信誉凭证）
5. 写来源   → 汇总进 `OV.src`，页面底部渲染成「核验说明」节
```

**核验日期必须写。** 半年后别人看这份攻略，得知道数据是什么时候的。

## 六、页面上怎么呈现来源

`OV.src` 数组逐条写，渲染在页面底部「核验说明」节：

```js
src: [
  '本攻略制作日期：2026-09-13。',
  '<b>票务规则</b>：依据国铁集团 2026 中秋国庆运输方案与 12306 官方公告 <span class="flag ok">已核验</span>',
  '<b>各站起售时间</b>：按发站查询 12306 <span class="flag ok">已核验</span>；实际以 12306 当日公告为准',
  '<b>景区预约</b>：内蒙古博物院 / 宁夏博物馆 / 甘肃省博物馆 官方小程序公告 <span class="flag ok">已核验</span>',
  '<b>店铺地址电话</b>：逐条重核，已订正旧行程书多处错误 <span class="flag ok">已核验</span>',
  '<b>天气</b>：行程临近前需重查，当前为历史同期参考 <span class="flag warn">待复核</span>',
  '行程安排与节奏为主观编排，仅供参考。'
]
```

- `<span class="flag ok">已核验</span>` —— 绿标，走完 S2
- `<span class="flag warn">待复核</span>` —— 赭标，只有 S3 或时效未到
- **不许出现没有来源标注的可核验数据**

## 七、绝对禁止（红线）

1. **编造电话号码 / 地址。** 这是最严重的，用户会照着去。
2. **拿旧资料当事实。** 用户给的旧行程书里，票价、预约规则、店址**默认全部过期**，一律当线索。
3. **把一手源和二手源混为一谈。** 自媒体转载不能标「已核验」。
4. **同一信息伪造多个来源。** 一条信息只能有一个来源，不能写成"多源确认"。
5. **对查不到的内容用"通常""一般"糊过去然后写成肯定句。** 不确定就写不确定。
6. **不标核验日期。** 没有日期的核验等于没有核验。
