# 旅行攻略 · 全流程构建（全国适用）

## 适用范围

- **全国任意目的地**（中国内地全流程适用）。地域差异（配色 / 交通主力方式 / 证件 / 季节）→ `references/regions.md`
- **启动方式**：用户说 **「帮我做旅行攻略」** 即进入本流程，从阶段 ① 追问开始。
- 中国香港 / 中国澳门 / 中国台湾：主流程可用，需额外补出入境证件与当地交通模块；出境不在范围。

## 跟用户的对话顺序（就这三步）

**这是跟用户交互的主线，别问散。**

### 第 1 步 · 去哪几个城市，从哪出发

> 「这趟想去哪几个城市？**从哪个城市出发？**」
> 顺序不用他说，我来排。没想好就给四种组合类型挑：环线 / 双城 / 单城 / 放射。

### 第 2 步 · 城市之间用什么交通工具

**能判断就直接判断，判断不了就给选项让他选：**

> 「城市之间想坐什么？**✈️ 飞机 ｜ 🚄 火车 ｜ 🚌 大巴 ｜ 🚗 包车** —— 或者你说"帮我选"，我按距离给你定。」

判断依据（速查表见 `references/itinerary.md` 第 1.5 节）：

| 距离 | 直接给建议 |
|---|---|
| < 300 km | 大巴或高铁 |
| 300–1200 km | 高铁为主 |
| > 1200 km | 飞机 |
| 无铁路 / 景区分散 | 包车 |

### 第 3 步 · 城市里有什么：景点 / 美食 / 怎么买票

按城市逐个过，**三件事一起问、一起给**：

| 事项 | 来源 | 说明 |
|---|---|---|
| **景点 · 选哪些** | 官方导览 + 联网搜索 | 选点四层法见 `itinerary.md`；候选清单让用户挑 |
| **景点 · 介绍 / 玩法** | **小红书高赞攻略**（指定） | 只取经验类内容（玩法、光线、避坑） |
| **📸 打卡点 / 机位** | **小红书高赞攻略**（指定） | 每城 5–8 个；给「怎么拍 + 几点拍 + 怎么去」，自动生成导航按钮 |
| **🍜 美食** | **大众点评**（指定） | 店名 / 招牌菜 / 人均 / 评分；地址电话**必须再和高德交叉核一遍** |
| **怎么买票** | 景区官方渠道优先 | 公众号 / 小程序 / 官网 → OTA 备用。规则见 `ticketing.md` |

⚠️ **小红书的边界**：它是 UGC，**票价 / 预约规则 / 开放时间 / 地址电话一律不能用它**，
必须走官方源。且页面标注写「据小红书高赞攻略整理」，**不能标「已核验」**。

**美食的产出形态**：每城列 3–6 家，写成 `CITIES[].eat[]`，含
`店名 · 招牌菜 · 人均 · 地址（门牌/建筑哪一侧）· 电话 · 营业时间`。
地址电话逐条核，**旧资料里的几乎都是错的**。

## 数据来源（这个 skill 的内容从哪来）

> ⚠️ **本 skill 没有内置景点库 / 店铺库 / 交通资料库。**
> 它不存任何目的地数据 —— 每一份攻略的每个地址、电话、票价、预约规则，都是**跑这一遍时现查的**。

来源按可信度分五层，**每条可核验数据都要能落到某一层并在页面上标明**：

| 层 | 来源 | 标法 | 用于 |
|---|---|---|---|
| **S1** | 用户提供 | `用户提供` | 已出票班次、已知开售时间、人数、硬约束 |
| **S2** | 官方一手源 | `已核验 · 日期` | 12306 / 景区官网·公众号·小程序 / 高德 / 气象台 |
| **S3** | 联网搜索 | `已核验` 或 `据公开信息` | 找官方入口、确认最新变动 |
| **S4** | WorkBuddy 能力 | — | ImageGen 配图、发布链接（**缺失可降级**） |
| **S5** | 模型先验 | 仅限通用常识 | 行程节奏 / 方位量级；**票价、电话、门牌号、预约规则一律不可用** |

**三层红线**：
1. **电话号码、门牌地址、票价、预约规则、起售时刻** —— 必须走 S1/S2/S3，查不到就留白标注，**绝不编造**。
2. **用户给的旧行程书默认全部过期** —— 当线索，不当事实。
3. **核验日期必须写进页面** —— 没有日期的核验等于没核验。

完整分层表、查询入口、各类数据的核验顺序、"信息少时能做出什么"的预期对照表 → **`references/sources.md`**

## 七个阶段

```
① 追问  → ② 行程设计 → ③ 核实 → ④ 配色 → ⑤ 配图 → ⑥ 构建 → ⑦ 验证发布
   ↑必须     ↑选点+连线    ↑最耗时    ↑用户选    ↑图生图     ↑模板填数    ↑CDP + 上线
```

每阶段做完再进下一个，**别跳步**。下面逐段说。

> **② 是"设计"，③ 是"查证"，别搞混。**
> 先决定去哪几个点、怎么连线（②），再去查这些点的票价和预约（③）。
> 反过来做会浪费大量时间核一些根本不会去的景点。

## ① 追问（结构化，不是闲聊）

**这是决定成品质量的一步。** 用户给的信息通常是残缺的，必须主动问齐。

**入口就是两问，别跳：**

1. **要去哪几个城市？**（从哪出发）
   → 用户没想好，就给四种组合类型让他挑：**环线型 / 双城型 / 单城深度型 / 放射型**
2. **城市之间想怎么走？** 把这四个摆出来选：**✈️ 飞机 ｜ 🚄 火车 ｜ 🚌 大巴 ｜ 🚗 包车**
   → 用户说"你帮我选"就按距离出方案，速查表在 `references/itinerary.md` 第 1.5 节

⚠️ **别一上来就问"航班号是多少"** —— 用户可能连城市都还没定。

- 完整问题清单与话术 → `references/interview.md`
- 原则：**分批问、给选项、允许"待补"**。每批 3–4 个问题，用选项化提问（用户习惯先看候选再定）。
- 必须挖出来的五类信息：
  1. **目的地与城际方式**：哪几个城市、坐什么去 ← **入口，先问这个**
  2. **骨架**：出发/返程的航班车次时刻、**人数是否中途变化**（这是最容易翻车的点）
  3. **硬约束**：已出票的、必须赶上的、接人送人的时刻
  4. **票务**：哪些已买、哪些要抢、开售时间用户知道吗
  5. **偏好**：吃/买想不想要、节奏松紧、预算档位

产出：一份**决策台账**（形式见 interview.md），后续所有步骤以它为准。
台账里每条标 `[已确认]` / `[待补]` / `[冲突]`，**冲突项必须回问用户**。

⚠️ 如果用户给了旧的行程书（PDF/docx），先抽文本：
```python
import pymupdf                      # PDF
doc = pymupdf.open(path); text = "\n".join(p.get_text() for p in doc)
```
或用 skill `markitdown-skill`。**旧文档里的人数假设、票价、预约规则几乎都是过期的**，一律当作线索而非事实。

## ② 行程设计（选哪些景点，城市间怎么走）

**这是攻略的智力核心。景点不是查出来的，是设计出来的。**

> 完整方法论（选点四层法 / 时长估算 / 日编排五规则 / 走廊判定 / 交通排序 / 可行性校验）→ `references/itinerary.md`

一句话版流程：

```
锚点识别 → 城市定位 → 候选四层 → 时长估算 → 日编排 → 交通串联 → 可行性校验
（钉死的）  （为什么来） （必去/主题/顺路/机动）  （含摆渡）  （2-3个/天）  （不走回头路）  （三条铁律）
```

**做对三件事这个阶段就稳了：**

1. **每个城市写一句"为什么来"** —— 说不出这句话的城市，考虑砍掉。
   多塞一个"路过城市"会挤掉真正值得的地方。
2. **候选分层让用户挑** —— 每城列 6–10 个，分 `必去 / 主题 / 顺路 / 机动` 四层，
   **用清单形式给用户选**（用户习惯先看候选再定），别自己闷头决定。
3. **算时长要含隐性成本** —— `游玩时长 + 往返交通 + 排摆渡/索道`。
   🔴 最大的坑：**景区大门 ≠ 核心景点**，很多要再坐 30–60 分钟摆渡车。

**交通三原则**：不走回头路 → 班次可行性优先 → 总时间成本最小。
**三条铁律**：到达日不排满 ｜ 单日车程 > 5 h 就拆两天 ｜ 末班车后要有过夜方案。

**产出：一张行程骨架表**（日期 / 城市 / 交通班次时刻 / 主点 / 宿）——
**这张表确认后才进下一步**，它是 ③ 核实、⑥ 构建的全部依据。

📌 走廊类型必须判定对（详见 itinerary.md）：
东部城市群 = 高铁；**西部大环线 = 包车为主，不是高铁**。判错全盘错。

📌 选完点之后，**每城的「美食（大众点评）+ 门票购买渠道」进 ③ 核实**去逐条落实。

## ③ 核实（别照抄旧资料）

**先读 `references/sources.md`** —— 它规定了这个阶段的方法论：五层来源分层、各类数据的官方查询入口、核验顺序、以及"查不到怎么标"。

核实的执行顺序：

```
1. 列清单 → 这份攻略要写哪些可核验数据？
2. 分来源 → 每条归到 S1~S5，标出必须去 S2 核的
3. 查证   → S2 优先 → S2 不通走 S3 → 都不到标「以官方当日公告为准」
4. 记日期 → 每条标核验日期
5. 写来源 → 汇总进 OV.src，渲染成页面底部「核验说明」节
```

国内攻略最容易出错的三块，**逐条重核**：

1. **🍜 美食店 —— 来源：大众点评**
   取「店名 · 招牌菜 · 人均 · 评分 · 地址 · 电话 · 营业时间」。
   🔴 **地址电话必须和高德地图交叉核**（点评地址常是商户自填旧址，高德 POI 更准），
   两源一致才写进页面。写法：`区 + 路 + 门牌`（如「新城区锡林郭勒北路 巴彦塔拉饭店 1 层北侧底商」）。
   同名老字号要写清是哪家店。
2. **预约规则 —— 来源：景区官方公众号 / 小程序 / 官网**
   每个馆/景区的「提前几天 + 几点放票 + 周几闭馆」都要查**最新公告**。
   - 常见坑：旧资料写"需预约"实际已取消；旧资料写"需分时预约"实际改为凭身份证直接进。
3. **票价 + 开放时间 —— 来源：官方最新公告**
   尤其旺季会调价、提早闭园。OTA 票价可参考，**以官方为准**。
4. **景点介绍 / 玩法 / 机位 —— 来源：小红书高赞攻略**（指定）
   只取经验类内容（玩法顺序、拍照机位、最佳光线、排队实况、避坑）。
   🔴 **票价 / 预约 / 开放时间 / 地址电话一律不能用它** —— 那些必须走官方源。
   页面标注写「据小红书高赞攻略整理」，**不标「已核验」**。
   取用时看**收藏数**、剔软广、**3 条以上不同作者提到才算共识**。
   **📸 每城另出 5–8 个打卡机位**，每个给「怎么拍 + 几点拍 + 怎么去」，
   方法论与避坑 → `references/checkpoints.md`

详细来源清单（含每类数据的首选源与交叉核验）→ `references/sources.md` 第三节

**再加一项地域相关的**（按目的地补）：
- 边境地区查**边防证**要求；高原线路留**适应期**并标海拔
- 确认主力交通方式（大环线是包车，不是高铁）
- 是否落在旺季限流 / 淡季闭园 / 天象窗口
→ 逐项对照 `references/regions.md` 第四、五节

票务时间规则（预售期、起售时刻、候补、捡漏窗口、儿童票）→ `references/ticketing.md`

**标 `已核验` 才写进页面**，没核到的写"以官方当日公告为准"。

## ⑤ 配图（系列一致性）

**每城一张横向长卷封面，全部与总览图同风格。**

详细手法见 skill `series-illustration-consistency`（**可选**，本条已自足），核心三条：

1. **总览图当母版做图生图**（`image1` + `input_fidelity: "high"`），prompt 里只替换地标清单 —— 风格才咬得死。
2. **每城 5–6 个地标横向铺开**，从左到右写；天空占上部 40%、地平线压到 60–65%。
3. **串行生成 + 每张独立 `output_dir`**（并行会互相覆盖）。

后处理统一：裁掉右下角水印 `crop((0,0,w,h-135))` → `resize((1280,740))` → JPEG q84。**覆盖前先备份旧图**到 `img/final_v1/`。

成本：每张 5–10 额度，**开工前先告诉用户总量**。
没有配图额度时走降级路径（用户自备照片 / CSS 纯色封面）→ `references/portability.md` 第三节。

## ⑥ 构建（数据驱动，不是手写 HTML）

**不要从零写 HTML/CSS。** 用 `assets/template.html` 当骨架：

```bash
python scripts/scaffold.py --out "D:\DeepSeek\输出\20260913_川西环线" \
       --title "川西环线 · 旅行攻略" --brand "川西环线" --theme A
```

它做的事：建目录（`img/final` `img/_raw` `build`）→ 拷模板 → 套用配色主题 → 填标题与品牌 → 写一份 `TODO.md` 待办清单。
城市数**不用告诉它** —— `PAGES` 由 `CITIES` 自动生成。

然后**只改数据，不动渲染逻辑**。要改的 5 个数据块（结构见 `references/data-schema.md`）：

| 块 | 内容 |
|---|---|
| `CFG` | 标题、品牌、封面图、起止日期、总天数、`dayMap`（日期→城市）、页脚 |
| `PLANE` / `TRAIN` / `BOOK` | 机票 / 火车票 / 需预约门票，含**开售时间**与**当前状态** |
| `CITIES` | 每城：`days`（逐日行程）/ `eat`（吃）/ `buy`（买）/ `walk`（步行路线）/ `shots`（拍照点） |
| `OV` | 总览页、票夹页、应急页的表格与清单 |
| `PAGES` | 页面注册 —— **已由 `CITIES` 自动生成，不用手改** |

**增删城市只改 `CITIES`**：`PAGES` 会自动跟随生成，Tab 顺序 = `CITIES` 顺序，`id` 自动对齐。这样就不会出现"数据里加了城市、Tab 里没加"的错。

**关键：文件太长必须分次写。** 单次 Write 超长会报 `file_path expected string` 而被截断。做法：
先写含占位符的骨架 → 再用多次 Edit 逐个替换占位符。

实现的三个功能，一个都不能少：
- **顶部封面随城市切换**（`show()` 里读 `CITIES[k].img`）—— 最容易漏，漏了用户会说"图没变"
- **当天自动定位城市**（`todayCityId()`）
- **距出发 N 天实时倒计时**（`tick()` + `setInterval`）

移动端必备：`<meta viewport>`、`max-width:720px` 居中、表格 `table-layout:fixed` + `word-break`、按钮 `:active` 位移反馈、`tel:` 拨号、`uri.amap.com/search?keyword=` 高德导航。

## ⑦ 验证 → 发布 → 兜底

### a. 本地验证（必须做，别靠肉眼猜）
```bash
python scripts/verify.py --dir "<项目目录>" --shot "<项目目录>/_verify.png"
```
**一条命令搞定**：自动起本地服务（空闲端口）→ 起无头 Chromium（自动探测）→
逐 Tab 点击并报告「封面 / 标题 / 横向溢出 / undefined / 图片加载」→ 收尾清理。

只验线上（不起本地服务）：
```bash
python scripts/verify.py --url "https://xxx.app.workbuddy.host/"
```

只看版式（三宽度并排出图）：
```bash
python scripts/shot_preview.py "<项目目录>/<主文件>.html"
```
`verify_tabs.js` 在"所有 Tab 共用同一张封面"时会**主动告警** —— 这正是最容易漏的那个 bug。

三个必记点（血泪）：
- **别用 `--window-size` 截窄屏** —— Windows 125% 缩放下 390 实际渲染成 481，右侧被硬裁，会让你误判"表格溢出"。用 `Emulation.setDeviceMetricsOverride`（verify.py 已内置）或 iframe 外壳。
- **改过图 / 换过资源后**，必须注入 JS 测 `img.naturalWidth===0` 确认真加载了（verify_tabs.js 已含）。
- **浏览器必须是 Chromium 系**（CDP 依赖）；找不到时用 `BROWSER_PATH` 指定。

### b. 发布上线
```bash
python scripts/prep_publish.py --dir "<项目目录>"        # 重建 publish/（含 index.html + guide.html 双入口）
```
然后调 `workbuddy_sites_deploy`（`updateExistingApp: true` 用于更新已有应用）。
发布前体检：抓 DOM 搜 `undefined`、搜关键渲染文本、确认无残留占位符（`prep_publish.py` 末尾会自动检查）。

### c. 破缓存（血泪区）
托管网关**忽略 query string**，`?v=2` 在服务端不构成新资源。
⇒ **改图必须换文件名**：`hohhot.jpg` → `hohhot-v3.jpg`，然后批量替换引用（三种引号形态都要覆盖）。
⇒ 给用户兜底话术：用带 query 的入口地址访问一次（`https://xxx/?v=3`），入口 HTML 换 URL 对浏览器缓存 key 有效。

### d. 离线兜底
```bash
python scripts/make_offline.py --dir "<项目目录>"
```
图片全部 base64 内联，产出零外部请求的单文件（约 1.5 MB）。攻略的倒计时/Tab 全在本地算，脱网完全可用。

## 铁律（每条都是踩过的）

1. **用户说"线上没变"，先 `grep` 数据有没有被渲染，再查缓存。**
   一次真实翻车：花三轮查哈希/响应头/CDN，真因是 `CITIES[].img` **定义了但没有任何渲染函数读它**。
   顺序：`curl+md5` 判服务端 → 零缓存无头判客户端 → **`grep` 字段名判"到底用没用"**。
2. **人数变化必须在追问阶段挖出来。** 旧行程书按「2 大 1 小」写、实际「1 人 + 1 大 1 小」，全篇费用和住宿作废。
3. **图片资源并行生成会互相覆盖**，串行 + 独立目录。
4. **配图风格不一致，八成是构图范式不同**（长卷 vs 特写），不是画风 —— 光调色没用，要整张重画。
5. **单次 Write 长文件会静默截断**，用骨架 + 多次 Edit。
6. **别把公共资源写成绝对路径**，发布目录里一律相对路径。
7. **每个可核验数据都要有来源和核验日期。** 页面底部「核验说明」节逐条写依据。
   **电话 / 门牌 / 票价 / 预约规则 / 起售时刻 —— 查不到就留白标注，绝不编造。**
   一份"框架完整 + 数据诚实"的攻略，远好过"内容丰满 + 数据可疑"的攻略。
   分层规则与查询入口 → `references/sources.md`
